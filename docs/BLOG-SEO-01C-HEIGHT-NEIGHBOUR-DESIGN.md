# BLOG-SEO-01C — Page B: правовой и контентный дизайн статьи о высоте забора между соседями

**Статус:** Phase 0, design only. Статья, route, metadata, schema, sitemap, Page A, service pages и изображения не изменены.

**Дата правовой проверки:** 11 сентября 2026 года

**Git baseline:** `1685a81761feee82c7f2b9e132c66d5f3b87836e`

**Будущий canonical URL:** `https://www.masterzabor.by/blog/vysota-zabora-mezhdu-sosedyami-v-belarusi`

**Primary query:** `высота забора между соседями`

## 1. Executive verdict

Page B нужна как отдельная specialist page для владельца обычного участка, предоставленного для строительства и обслуживания одноквартирного жилого дома. Она должна сразу отвечать на числовое ожидание пользователя, но не заменять одну устаревшую универсальную цифру другой.

Главный юридический вывод на дату проверки:

> В проверенных действующих общереспубликанских нормах не установлена единая максимальная высота или обязательная светопрозрачность ограждения между соседями для обычного приусадебного участка. Прежние требования пункта 6.3.18 СН 3.01.03-2020 перестали действовать 28 ноября 2023 года. Это не делает допустимым любой забор: сохраняются условия отвода и ограничения участка, применимая утверждённая проектная документация, установленная граница и обязанность не нарушать права других лиц.

Это `LEGAL CONCLUSION`, ограниченное указанным типом участка и перечнем проверенных национальных актов. В статье нельзя сокращать его до безусловных формул «ограничений нет», «можно ставить 3 м» или «сосед ничего не решает».

Page B не создаёт новые правила и не выдаёт практический совет за норму права. Для спорного конкретного участка она должна направлять читателя к документам и компетентному органу, а не обещать юридическую определённость по одному описанию забора.

## 2. Контекст repository и reference implementation

На baseline `HEAD`, `main` и `origin/main` совпадали: `1685a81761feee82c7f2b9e132c66d5f3b87836e`. Рабочее дерево до этой фазы было чистым. Page A уже реализована в `content/blog-posts.ts` и является утверждённым техническим и визуальным reference implementation, но не контентным шаблоном.

Фактическая blog architecture:

- `BlogPost` содержит `slug`, `title`, `metaTitle`, `metaDescription`, `excerpt`, HTML `content`, `publishedAt`, необязательный `updatedAt`, `image`, необязательный `imageAlt` и `tags`;
- `app/blog/[slug]/page.tsx` строит все article routes из `blogPosts` через `generateStaticParams()` при `dynamicParams = false`;
- metadata, canonical и Open Graph image формируются из записи поста;
- шаблон выводит один H1, excerpt, tags, hero через `next/image`, Article и Breadcrumb JSON-LD, sidebar CTA, автоматический блок из трёх других статей и нижний `QuizForm`;
- scoped typography находится в `app/blog/[slug]/page.module.css` и задаёт ритм H2/H3, абзацев, списков и ссылок, включая mobile presentation;
- hero Page A — WebP `1200 × 630`, 190 410 байт; шаблон также ожидает размер `1200 × 630`, использует descriptive alt и передаёт image в Open Graph;
- Article JSON-LD сохраняет `datePublished = publishedAt`, а `dateModified = updatedAt ?? publishedAt`;
- sitemap берёт статью из `blogPosts`; её `lastmod` равен `updatedAt ?? publishedAt`, а `/blog` получает максимальную дату среди видимых постов и собственной template freshness.

Следствие для будущей реализации: Page B добавляется в существующую data-driven архитектуру и переиспользует текущий layout, CSS Module, schema и CTA без изменения blog template. Автоматический блок «Другие статьи» не заменяет контекстные связи A ↔ B.

## 5. Unresolved legal gaps

1. **Нет одной прямой нормы с формулой «согласие не требуется независимо от высоты и материала».** Вывод L-07 основан на отсутствии blanket requirement в проверенных национальных правилах и на общих пределах прав собственника/землепользователя. В статье нужно писать «общего требования не установлено/не найдено», а не «согласие точно не нужно в любой ситуации».
2. **Не проведена исчерпывающая проверка каждого местного решения, специальной территории и индивидуального проекта по всей Беларуси.** Национальный вывод не отменяет применимые местные, территориальные или индивидуальные условия. Статья должна советовать точечную проверку при наличии такого признака, но не пугать всех читателей полным permission route.
3. **Не подтверждена отдельная национальная методика оценки влияния именно соседского забора на инсоляцию.** Нельзя публиковать проценты, часы, расстояния или автоматический тест затенения без отдельного источника. Возможное нарушение прав оценивается по фактам, а не по выдуманной fence-specific формуле.
4. **Не исследовалась судебная практика по конкретным высотам, материалам и видам вреда.** Не приводить «обычную позицию судов», вероятность исхода, штрафы, сроки или обязательный способ защиты.
5. **Не установлено универсальное распределение расходов и обслуживания общего ограждения.** Честный ответ Page B — общей обязанности одной стороны в проверенных актах не найдено; конкретный режим зависит от собственности, договора и обстоятельств.
6. **Page C не проходит полную правовую валидацию в этой фазе.** На Page B допустим только короткий carve-out о другом режиме садоводческого товарищества без подробных чисел, таблицы сторон и ссылки на ещё не существующую страницу.

Эти gaps не блокируют Page B. Они определяют осторожный язык и запрещают ложную конкретику.

## 8. Cannibalization audit Page A → Page B

Текущая Page A уже содержит три зоны пересечения:

1. подраздел «Что изменилось 28 ноября 2023 года» с отменой старых 2 м;
2. H2 «Нужно ли согласие соседа: короткий ответ» из трёх абзацев про согласие, высоту, материал, водоотвод, глухой забор, затенение и спор;
3. H2 о границе и старом заборе с маршрутом установления/восстановления.

После публикации Page B рекомендованы только точечные изменения Page A:

- оставить дату и суть отмены пункта 6.3.18 как supporting fact, но не разворачивать ответ о допустимой высоте; завершить абзац естественной ссылкой на Page B;
- сократить neighbour/consent-блок до одного короткого переходного абзаца: общего согласия как разрешительного документа обычно нет, но граница и права соседа сохраняются; подробности о высоте и сплошном заполнении — на Page B;
- оставить boundary-блок Page A, потому что он обслуживает документы и pre-installation route; на Page B раскрывать только соседский сценарий, старый забор и выбор действия при споре;
- не менять H1, URL или primary permission intent Page A.

Рекомендуемое место A → B: внутри текущего H2 о согласии, после короткого ответа. Семейства anchors: `правила высоты забора между соседями`, `что учитывать при выборе высоты и сплошного заполнения`. Не повторять exact primary query механически.

Рекомендуемое место B → A: в блоке «Что проверить вместо одной цифры», после краткого перечисления проекта, границы и ограничений. Семейства anchors: `что проверить до установки забора`, `нужен ли отдельный документ перед монтажом`.

## 9. Recommended article outline

Структура объединяет близкие пункты B0 и не повторяет механически схему H2 → список → вывод.

### Вступление под H1

Два коротких абзаца. Первый даёт ограниченный прямой ответ: для обычного приусадебного участка действующие проверенные национальные нормы не задают единого максимума; прежние 2 м больше не универсальная норма. Второй сразу ставит предел: нужно проверить тип участка, документы/проект, границу, ограничения и права соседа.

### H2. Для какого участка действует этот ответ

Отделить обычный участок с одноквартирным жилым домом от садоводческого товарищества и специальных территорий. Carve-out о товариществе — один короткий абзац без 1,7 м/50%, подробной таблицы и ссылки на несуществующую Page C.

### H2. Почему правило «не выше 2 м» устарело

Объяснить дату 28.11.2023, механизм новой редакции подраздела 6.3 и актуальную проверку Изменения № 3. Не превращать историю нормы в длинную хронологию.

### H2. Что проверять вместо одной универсальной цифры

Коротко назвать применимую утверждённую проектную документацию, условия/ограничения участка и установленную границу. Здесь поставить B → A для полного permission checklist. Не повторять регистрацию, красные линии, сети и полный маршрут исполком/архитектура.

### H2. Нужно ли согласие соседа и кто отвечает за общий забор

Объединить consent и ownership/cost supporting intents. Дать три разграничения:

- общего согласия только из-за высоты или материала в проверенных национальных актах не найдено;
- это не разрешение нарушить границу или права другого лица;
- общей обязанности одной стороны строить, обслуживать или оплачивать забор также не найдено; совместные параметры и расходы лучше фиксировать отдельно.

Не давать шаблон соглашения и не обещать юридическую силу бытовой переписки.

### H2. Высокий или сплошной забор: где возникает риск

Развести `DIRECT RULE`, `LEGAL CONCLUSION` и practical risk. Объяснить, что высота и материал не дают автоматического ответа; важны режим, фактическое влияние, граница и доказуемое нарушение прав. Можно привести нейтральные ситуации для проверки — водоотвод, доступ для работ, устойчивость/ветровая нагрузка, фактическое влияние на соседнее пользование — без выдуманных норм инсоляции и без утверждения, что любой дискомфорт равен нарушению.

### H2. Где проходит линия забора и почему старого ограждения недостаточно

Понятно объяснить фиксированную и нефиксированную границу, роль координат/межевых знаков и почему привычная линия старого забора не заменяет землеустроительные материалы. Не превращать раздел в полное руководство по кадастровым работам.

### H2. Что делать до монтажа, если граница или влияние спорны

Дать короткую последовательность: остановить разметку и закупку необратимых элементов; собрать документы; определить, устанавливалась ли фиксированная граница; заказать надлежащую работу при необходимости; сформулировать конкретный предмет разногласия; выбрать компетентный маршрут по статье 108. Не указывать сроки, штрафы или гарантированный результат.

### H2. Рабица, евроштакетник и профнастил: выбирать по задаче, а не по ярлыку «законно»

Сравнить конкретные свойства: открытость и обзор, приватность, вентиляция, ветровая нагрузка, обслуживание и конфигурация просветов. Название материала не подтверждает правовую допустимость. Здесь уместны service links и спокойный переход к `/tseny` после полезного ответа.

### H2. Короткие ответы на частые вопросы

Оставить 5 вопросов без повторения всей статьи:

1. Есть ли сейчас максимальная высота забора между соседями у частного дома?
2. Действует ли прежнее правило 2 м?
3. Можно ли поставить забор высотой 3 м?
4. Нужно ли письменное согласие соседа на высокий или сплошной забор?
5. Можно ли считать старый забор границей участка?

Отдельный FAQ-schema redesign не нужен: текущий blog template выводит Article/Breadcrumb JSON-LD. Вопросы остаются обычным содержимым, если отдельная schema-stage не докажет необходимость и полное соответствие видимому тексту.

### Правовые источники и дисклеймер

В конце дать компактный список только официальных источников и дату проверки. Дисклеймер: материал информационный; для спорного участка опираться на документы и письменное решение/разъяснение компетентного органа.

## 14. Semantic freshness impact

По действующей SEO-02 модели будущая implementation-stage должна обновить только реально изменившиеся поверхности:

| Surface | Freshness action |
| --- | --- |
| новая Page B | задать честный `publishedAt` датой реальной публикации; `updatedAt` при первой публикации не нужен |
| `/blog` | отдельная ручная дата не требуется: sitemap автоматически возьмёт максимум `publishedAt/updatedAt` видимых постов |
| Page A | если текст сокращён и добавлена A → B ссылка, сохранить `publishedAt` и установить реальный новый `updatedAt` |
| `/zabory-iz-profnastila` | только при фактическом добавлении incoming link обновить semantic owner этой service detail surface; не менять общую service-card freshness |
| `/zabory-iz-evroshtaketnika`, `/tseny`, другие URL | исходящая ссылка из Page B не меняет их rendering; даты не трогать |

Не использовать build/deploy/current time и не ставить blanket date другим URL. Если incoming service link реализуется через условный shared component, freshness всё равно получает только реально изменившийся rendered service URL, а не все шесть service pages.

## 16. Acceptance criteria for future implementation

### Content and law

- первый экран отвечает на primary query без ложной универсальной цифры;
- область применения «обычный приусадебный участок с одноквартирным домом» видна до деталей;

- URL ровно `/blog/vysota-zabora-mezhdu-sosedyami-v-belarusi`;

- коммерческие ссылки не превышают лимит и находятся после полезного ответа;
